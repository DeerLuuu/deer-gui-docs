# 布局不变式（I-1 ～ I-8）

`layout()` 的行为由八条不变式定义，**每条都有对应测试**（`crates/deer-layout/tests/layout_invariants.rs`）。这八条是布局引擎的行为契约：文档与直觉冲突时，以不变式为准。

## 一览

| # | 不变式 | 一句话 | 实践含义 |
|---|---|---|---|
| I-1 | **纯函数** | 不改输入树，只回几何表 | 想改布局要自己改树再重算；放心复用同一棵树 |
| I-2 | **确定性** | 同树 + 同盒子 ⇒ 逐位相同输出 | 无时间、无随机、无环境探测；可做快照测试 |
| I-3 | **自底向上** | 先算子节点固有尺寸，父容器再分配 | `measure_tree` 与 `layout` 的中间量一致 |
| I-4 | **像素取整** | 几何全部整数像素 | 类型是 `f32` 但值永远是整数；没有半像素模糊 |
| I-5 | **不假设拥有窗口** | 根盒子由宿主给，根不撑满 | 想让根占满就给根显式尺寸（或让宿主按内容给盒子） |
| I-6 | **不越界** | 结果夹在可用空间内 | 显式尺寸也只是「上限内的请求」 |
| I-7 | **分配尺寸 ≠ 可用空间** | 父分配的主轴尺寸必须被采信；百分比相对父**内容盒**解析 | `grow` 分配的空间不会被静默丢弃；`50%` ≠「父已分配空间的一半」 |
| I-8 | **主轴 = sum(子)，交叉轴 = max(子)** | 容器固有尺寸按方向语义不同 | `Row` 的高由最高的子节点决定；`Column` 的宽由最宽的子节点决定 |

## 两条最容易被误解的

### I-7：分配尺寸 vs 可用空间

这是 deer-ui 原型时代 **B-2 缺陷**的显式建模：父容器**分配**给子节点的主轴尺寸（`grow` 算出来的）
必须被子节点采信；「可用空间」只是上限。把两者混为一谈，`grow` 分配的空间会被静默丢弃。

同理，**百分比相对父的内容盒**解析（内边距以内的区域）。传错基准是个静默错误：
布局仍然「有值」，只是值错了 —— 测试 `I-7` 专门钉住它。

### I-5：根不撑满

宿主给的盒子是**上限不是命令**。根节点的「分配尺寸」= 它的固有尺寸 —— 除非根自己有显式尺寸。
所以第 3 步示例里根节点写了 `.w(280.0).h(160.0)`，画布却是 300×200 —— 根只占 280×160。

## 与滚动 / 换行的交互

- **滚动容器**（`Column + scroll`）：子节点主轴**不被视口夹取**（否则「内容高于视口」这个前提
  自己就不成立），`grow` 失效（没有剩余空间可分）；交叉轴仍然夹到内容盒；
- **换行文本**（`Text + wrap` + 显式像素宽度）：固有高 = 实际行数 × 行高 —— 行数只有一处定义
  （`Measure::wrap`），布局预留与渲染绘制不会分叉。

## 怎么验证

```sh
cargo test -p deer-layout          # 布局不变式全量断言（无 GPU 也能跑）
cargo run -p deer-gui --example geometry   # 布局与命中测试的可视示例
```

给布局引擎提 PR 时：每条不变式的测试就是验收判据；改语义必须先改测试、说明
「哪条不变式变了、为什么」，并同步更新本页与 [布局引擎 API](../api/layout.md)。
