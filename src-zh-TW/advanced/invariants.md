# 版面配置不變式（I-1 ～ I-8）

`layout()` 的行為由八條不變式定義，**每條都有對應測試**（`crates/deer-layout/tests/layout_invariants.rs`）。這八條是版面配置引擎的行為契約：文件與直覺衝突時，以不變式為準。

## 一覽

| # | 不變式 | 一句話 | 實踐含義 |
|---|---|---|---|
| I-1 | **純函式** | 不改輸入樹，只回幾何表 | 想改版面配置要自己改樹再重算；放心複用同一棵樹 |
| I-2 | **確定性** | 同樹 + 同盒子 ⇒ 逐位相同輸出 | 無時間、無隨機、無環境探測；可做快照測試 |
| I-3 | **自底向上** | 先算子節點固有尺寸，父容器再分配 | `measure_tree` 與 `layout` 的中間量一致 |
| I-4 | **像素取整** | 幾何全部整數像素 | 型別是 `f32` 但值永遠是整數；沒有半像素模糊 |
| I-5 | **不假設擁有視窗** | 根盒子由宿主給，根不撐滿 | 想讓根佔滿就給根顯式尺寸（或讓宿主按內容給盒子） |
| I-6 | **不越界** | 結果夾在可用空間內 | 顯式尺寸也只是「上限內的請求」 |
| I-7 | **分配尺寸 ≠ 可用空間** | 父分配的主軸尺寸必須被採信；百分比相對父**內容盒**解析 | `grow` 分配的空間不會被靜默丟棄；`50%` ≠「父已分配空間的一半」 |
| I-8 | **主軸 = sum(子)，交叉軸 = max(子)** | 容器固有尺寸按方向語意不同 | `Row` 的高由最高的子節點決定；`Column` 的寬由最寬的子節點決定 |

## 兩條最容易被誤解的

### I-7：分配尺寸 vs 可用空間

這是 deer-ui 原型時代 **B-2 缺陷**的顯式建模：父容器**分配**給子節點的主軸尺寸（`grow` 算出來的）
必須被子節點採信；「可用空間」只是上限。把兩者混為一談，`grow` 分配的空間會被靜默丟棄。

同理，**百分比相對父的內容盒**解析（內邊距以內的區域）。傳錯基準是個靜默錯誤：
版面配置仍然「有值」，只是值錯了 —— 測試 `I-7` 專門釘住它。

### I-5：根不撐滿

宿主給的盒子是**上限不是命令**。根節點的「分配尺寸」= 它的固有尺寸 —— 除非根自己有顯式尺寸。
所以第 3 步範例裡根節點寫了 `.w(280.0).h(160.0)`，畫布卻是 300×200 —— 根只佔 280×160。

## 與捲動 / 換行的互動

- **捲動容器**（`Column + scroll`）：子節點主軸**不被視口夾取**（否則「內容高於視口」這個前提
  自己就不成立），`grow` 失效（沒有剩餘空間可分）；交叉軸仍然夾到內容盒；
- **換行文字**（`Text + wrap` + 顯式像素寬度）：固有高 = 實際行數 × 行高 —— 行數只有一處定義
  （`Measure::wrap`），版面配置預留與渲染繪製不會分叉。

## 怎麼驗證

```sh
cargo test -p deer-layout          # 版面配置不變式全量斷言（無 GPU 也能跑）
cargo run -p deer-gui --example geometry   # 版面配置與命中測試的可視範例
```

給版面配置引擎提 PR 時：每條不變式的測試就是驗收判據；改語意必須先改測試、說明
「哪條不變式變了、為什麼」，並同步更新本頁與 [版面配置引擎 API](../api/layout.md)。
